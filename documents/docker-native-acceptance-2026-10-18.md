## 实机发现与修复

- Debian 系统 jq `1.7` 无法解析共享 Xray 生成器中的对象值加法，WS 首配也会失败。
  `992e274d` 补外层括号，输出语义不变；回归镜像保留默认 jq 并增加系统 jq。
  旧生成器加新测试实际失败，修复后 canonical 输出一致；定向总 `9.356` 秒。
- 新 TLS 首配未显式选择站点，legacy Nginx 首页返回 403。
  同一提交让新向导仅在当前包及待切换包都支持站点时写入 `site.default`，
  复用已有 Welcome 页面，不修改旧规格识别；setup 定向总 `85.643` 秒。
- SSH collector 的宿主运行目录未准备，Docker 自动创建为 `0755 root:root`，
  正式 3.40 的候选启用和失败恢复均被生产 `Directory` 的 `0700` 门禁拒绝。
  `8d607f55` 仅为启用 SSH 防护的规格安全创建/归一目录，复用现有 root 属主准备；
  普通部署不生成 collector 状态。旧实现加新测试准确失败，
  修复后的权限定向总 `4.280` 秒，覆盖真实 `Directory` 接受与重复准备。

正式版本失败后，先修正精确测试目录权限，再由生产 CLI 停用、恢复健康并重新启用，
才进行 SSH 真实封禁验收；不把这一人工修正宣称为正式版本已修复。
三个源码修复已本地签名提交，尚未进入新的正式发布；本任务没有推送或发布。
共享工具镜像只重建一次，未重复日常集合或 full。

## 宿主测试中断与恢复

Redirect 验证返回 `0` 后，执行停用 Redirect、启用 TProxy 的串行命令；
该命令未返回阶段退出码，原 SSH 会话即超时。随后 MSYS SSH、Windows 原生 SSH
和本机已配置代理通道均未恢复握手，测试 HTTPS `14443` 也超时。
一次独立 TCP 探测收到过 SSH banner，其余探测超时，不能据此判定整机停机、
TProxy 启用成功或某条规则已损坏。当前不能确认最后提交的规格及规则状态。
后续通过代理访问 `14443` 已通过 TLS 校验并收到测试 Python 服务的 HTTP `501`
响应，证明该时点测试服务仍在运行；SSH 握手仍未恢复。

源码复核显示 UID 模式的核心使用 host 网络和 root，OUTPUT 仅捕获 UID `65532`
主动连接，PREROUTING 先放行本机目的地址；这些证据尚不能解释失联原因。
需要控制台读取负载、内存、监听、mangle 计数、策略路由和部署锁 owner 后定位，
不根据时间先后将其写成已确认的 TProxy 缺陷。

控制台可先尝试生产撤销入口，立即拒绝仍由活进程持有的部署锁：

```bash
PADM_DOCKER_LOCK_TIMEOUT=0 padm-docker edit --tproxy-off --confirm PADM-DOCKER-EDIT
```

锁被占用时不要删锁或并行编辑。必要时核实唯一 `net-transparent` 容器的标签和
命令后，使用 `docker stop --time -1 <CID>` 等待 TERM 的归属审计清理，
再待原事务退出后撤销。禁止全表 flush、强杀 owner 或把重启当成清理成功。

Redirect 原始计数文件及本批后续日志仍在远端，已保留本机会话观察摘要；
恢复访问后必须取回、核对并继续验收。远端测试目录、TLS 目标
`padm-native-target4.service`、可能的透明代理资源及正式安装尚未确认清理。
本机公网客户端容器已确认不存在，不将远端未清理项写成已完成。
